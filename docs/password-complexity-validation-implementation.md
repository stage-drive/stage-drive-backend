# Валідація складності пароля — план реалізації

Читати після [CLAUDE.md](../CLAUDE.md) перед тим, як імплементувати або рев'ювати цю задачу.

## Джерело задачі

Баг-репорт проти **фронтенду** (`/register` на stage-drive-frontend): форма приймає пароль, що складається лише
з пробілів, лише з цифр (`123456`) або лише зі спецсимволів (`!!!!!!`), бо клієнтський валідатор не перевіряє
complexity і не робить `.trim()`.

**Чому цей план — у backend-репозиторії, а не у фронтенді:** клієнтська валідація — лише UX-зручність, її
можна обійти напряму через API (Postman, curl — так само, як ми самі тестували `/auth/register` протягом цієї
розробки). Єдине місце, де вимогу справді **не можна обійти**, — DTO-валідація на бекенді
(`class-validator`, вже обов'язкова частина стилю проєкту за CLAUDE.md: "Always validate incoming request
bodies using class-validator"). Фронтенд теж потребує еквівалентного фіксу для миттєвого фідбеку, але це
окрема задача в іншому репозиторії — тут фіксується лише backend-частина, яка є єдиним реальним захистом.

## Поточний стан — та сама слабка валідація в трьох місцях

Перевірено напряму по коду — всі три місця, де користувач/бекенд встановлює **новий** пароль, мають однаковий
набір правил і однакову діру:

| DTO / поле | Файл | Поточні decorators |
|---|---|---|
| `RegisterDto.password` | [auth.dto.ts](../src/modules/auth/auth.dto.ts) | `@MaxLength(72) @MinLength(8) @IsString() @IsNotEmpty()` |
| `ResetPasswordDto.password` | [password-reset.dto.ts](../src/modules/auth/password-reset.dto.ts) | те саме |
| `ChangePasswordDto.newPassword` | [users.dto.ts](../src/modules/users/users.dto.ts#L77) | `@MinLength(8) @MaxLength(72) @IsString()` (без `@IsNotEmpty`, але не критично — порожній рядок не пройде `@MinLength(8)`) |

Жодне з трьох не перевіряє склад символів. `@IsNotEmpty` перевіряє лише `value !== ''` — рядок із восьми
пробілів `"        "` **не є** порожнім рядком із погляду `class-validator`, тож він проходить `@IsNotEmpty` і
`@MinLength(8)` без проблем. Це відтворює точно ті самі три сценарії з баг-репорту (whitespace-only,
digits-only, specials-only), лише напряму через API, без фронтенда.

## Що НЕ чіпати (важливо)

- **`LoginDto.password`** — це пароль для *спроби входу*, а не для встановлення. Додавання complexity-перевірки
  сюди миттєво заблокує вхід **усім існуючим користувачам**, чиї паролі не відповідають новим правилам
  (зареєстровані до цього фіксу). Це найнебезпечніша можлива помилка в цій задачі.
- **`ChangePasswordDto.currentPassword`** — так само, це звірка з уже існуючим (можливо, "слабким" за новими
  правилами) паролем, не встановлення нового. Не валидувати за складністю.
- Існуючі паролі в БД **не мігруються і не інвалідуються** — новий валідатор впливає лише на *майбутні* спроби
  встановити/змінити пароль (`register`, `reset-password`, `change-password`), не на вже захешовані.

## Дизайн

### 1. Спільний regex + повідомлення — новий файл чи існуючий `auth.dto.ts`?

Три DTO в двох різних модулях (`auth`, `users`) використовують те саме правило. За CLAUDE.md/принципом
"three similar lines is better than a premature abstraction" — але тут це не три рядки, а один regex + одне
повідомлення, які мають лишатися **ідентичними** в усіх трьох місцях (розбіжність тут — реальний ризик, не
теоретичний: якщо хтось поправить складність лише в `RegisterDto`, `reset-password` і `change-password`
залишаться дірою). Тому виправдано винести в спільний файл:

`src/common/validators/password-strength.ts`:

```ts
export const PASSWORD_STRENGTH_REGEX =
  /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[^A-Za-z0-9\s]).+$/;

export const PASSWORD_STRENGTH_MESSAGE =
  'Пароль має містити щонайменше одну велику літеру, одну малу літеру, ' +
  'одну цифру та один спеціальний символ.';
```

Regex через lookahead-групи вимагає всі чотири класи символів одночасно в довільному порядку. Це автоматично
відхиляє всі три сценарії з баг-репорту:
- лише пробіли → жодного класу символів немає → fail;
- лише цифри (`123456`) → немає літер/спецсимволів → fail;
- лише спецсимволи (`!!!!!!`) → немає літер/цифр → fail.

Довжина (`@MinLength(8)`/`@MaxLength(72)`) лишається окремими decorators, як і зараз — regex не дублює цю
перевірку.

### 2. Застосувати в трьох місцях, зберігаючи існуючий порядок decorators

Порядок decorators важливий через коментар у [auth.dto.ts:22-25](../src/modules/auth/auth.dto.ts#L22) —
`class-validator` reєструє їх знизу вгору, і з `stopAtFirstError: true` найближчим до поля має бути
`@IsNotEmpty` (щоб на порожньому вводі саме "заповніть поле" перемагало, а не помилка формату). Новий
`@Matches` з complexity-правилом додається **над** усіма існуючими — тобто перевіряється останнім:

```ts
@Matches(PASSWORD_STRENGTH_REGEX, { message: PASSWORD_STRENGTH_MESSAGE })
@MaxLength(72, { message: 'Пароль занадто довгий.' })
@MinLength(8, { message: 'Пароль має містити щонайменше 8 символів.' })
@IsString()
@IsNotEmpty({ message: REQUIRED_FIELD_MESSAGE })
password: string;
```

Застосувати до: `RegisterDto.password`, `ResetPasswordDto.password`, `ChangePasswordDto.newPassword`.

### 3. Відкрите питання: `.trim()` для leading/trailing пробілів

Баг-репорт явно просить `.trim()`. Regex вище **вже покриває** всі три відтворені сценарії без trim (пробіли
самі по собі не містять жодного потрібного класу символів). Окремий, не описаний у репорті кейс — пароль із
випадковим пробілом по краях, що сам по собі складний: `" Password123! "`. Тут є два варіанти, і вони не
рівноцінні:

- **Variant A (рекомендовано): валідація "не трим", а відхилення.** Додати `@Matches(/^\S.*\S$|^\S$/, ...)`
  (не починається і не закінчується пробілом) як окрему перевірку, що **відхиляє** запит з повідомленням,
  а не мовчки змінює значення. Пароль, який дійде до `bcrypt.hash`, — рівно те, що ввів користувач.
- **Variant B (як буквально просить репорт): `@Transform(({ value }) => value?.trim())` перед валідацією.**
  Це **змінює** значення, яке піде в `bcrypt.hash`. Небезпека: якщо коли-небудь `LoginDto.password` теж
  отримає такий самий `@Transform` (а без цього trim на реєстрації створює пароль, який неможливо ввести
  на логіні через `bcrypt.compare` символ-в-символ) — це інша задача з іншим ризиком, і в цьому репорті вона
  не згадана. Мовчки трансформувати пароль користувача — сюрприз, який важко відлагодити ("я ж ввів саме
  такий пароль").

Рекомендація: **Variant A**. Він і закриває репортований клас багів, і не чіпає жодної існуючої поведінки
логіна. Остаточне рішення — за тим, хто приймає задачу; якщо оберуть Variant B, `LoginDto.password` теж
потребує ідентичного `@Transform`, інакше це створить новий, гірший баг (легітимний пароль з пробілом по
краю, який неможливо ввести повторно).

## Тест-план

Для кожного з трьох DTO (`RegisterDto`, `ResetPasswordDto`, `ChangePasswordDto`) — тести на новий
`PASSWORD_STRENGTH_REGEX`, ідеально як unit-тест самого regex/константи (не залежить від Nest-контексту):

- `"        "` (лише пробіли, 8 символів) → **не проходить**;
- `"12345678"` (лише цифри) → **не проходить**;
- `"!!!!!!!!"` (лише спецсимволи) → **не проходить**;
- `"password"` (лише малі літери) → **не проходить** (немає великої літери/цифри/спецсимволу — репорт прямо
  цього не називав, але це той самий клас проблеми, і regex це вже покриває безкоштовно);
- `"SecurePassword123!"` (наявний приклад у `@ApiProperty` цих самих DTO) → **проходить**.

Плюс (якщо обрано Variant A з розділу вище) — окремий тест на `" Password123! "` → відхилено з повідомленням
про пробіли на краях.

**Конкретний тест, який зламається без правки** (перевірено, не гіпотетично):
[test/app.e2e-spec.ts:527](../test/app.e2e-spec.ts#L527) — `PATCH /api/users/me/password` викликається з
`newPassword: 'Password2'` (літери + цифра, **без спецсимволу**) → після фіксу поверне `400` замість `200`.
Виправити на пароль, що відповідає новим правилам (наприклад, `'Password2!'`), **до** або **разом** з
основною зміною, інакше цей тест хибно виглядатиме як регресія самого фікса.

Що перевірено й **не зламається**: юзер `owner` у тому ж файлі сідиться напряму через
`bcrypt.hash('SecurePassword123', 10)` ([app.e2e-spec.ts:176](../test/app.e2e-spec.ts#L176)) — це прямий запис
у БД, минаючи `ValidationPipe`/DTO, тож логін-тести з цим паролем (`'SecurePassword123'`, без спецсимволу)
продовжать проходити, бо нова валідація застосовується лише на вході в `register`/`reset-password`/
`change-password`, не на вже існуючих хешах. Реєстраційні тести на рядках 1089–1172 того ж файлу вже
використовують `'SecurePassword123!'` (зі спецсимволом) — не зламаються.

## Чек-лист для рев'ю

- [ ] `PASSWORD_STRENGTH_REGEX`/`PASSWORD_STRENGTH_MESSAGE` визначені один раз у спільному місці, а не
      продубльовані з можливістю розійтися між трьома DTO.
- [ ] Regex застосовано до `RegisterDto.password`, `ResetPasswordDto.password`,
      `ChangePasswordDto.newPassword` — і **тільки** до них.
- [ ] `LoginDto.password` і `ChangePasswordDto.currentPassword` **не змінені** — жодної complexity-перевірки
      на полях, що звіряють уже існуючий пароль.
- [ ] Порядок decorators на кожному полі відповідає існуючій конвенції файлу (required-перевірка найближче
      до поля, complexity — найдалі/останньою).
- [ ] Якщо обрано `.trim()` (Variant B) — `LoginDto.password` отримав той самий `@Transform`, інакше це нова
      діра, гірша за початкову.
- [ ] [test/app.e2e-spec.ts:527](../test/app.e2e-spec.ts#L527) оновлено (`newPassword: 'Password2'` →
      щось зі спецсимволом), інакше цей конкретний тест почне падати.
- [ ] Інші existing тести з паролями-fixture все ще проходять (`npm test`) — жоден не почав падати через нову
      валідацію замість перевірки власної логіки.
- [ ] Нові тести на всі сценарії з баг-репорту (whitespace-only, digits-only, specials-only) присутні й
      проходять.
